# Signal Desk UI 重设计说明

## 1. 目标

为 Echo Offer 的首页、面试答题页和评估报告页建立统一的 Signal Desk 视觉系统。

这次改造只调整前端界面、文案、布局和状态展示，不改变简历解析、项目分析、面试答题、批量评分和报告接口的业务逻辑。

产品面向准备投递 Agent 应用工程师岗位的求职者。界面的核心任务是让用户完成三件事：把项目内容说清楚，完成无提示答题，看到具体且能复盘的面试反馈。

## 2. 设计原则

1. 工程感来自信息组织和排版，不来自 AI 术语、发光效果或装饰性动画。
2. 页面只告诉用户当前在做什么、下一步做什么、结果为什么如此。
3. 主要内容使用自然中文，内部实现术语不出现在主界面。
4. 评分结果必须回到具体回答和评分理由，不突出未经校准的总分。
5. 错误状态要保护用户已完成的工作，并给出直接可执行的下一步。

## 3. 视觉系统

### 3.1 色彩

| 用途 | 色值 | 说明 |
| --- | --- | --- |
| 深色结构 | `#182438` | 页头、进度栏、主要按钮 |
| 冷灰背景 | `#E9EDF2` | 工作区外层背景 |
| 内容底色 | `#F8FAFB` | 表单、问题和报告的阅读区域 |
| 信号蓝 | `#2F57D1` | 当前步骤、链接、有效状态 |
| 校验橙 | `#FF7043` | 当前动作、提醒、错误处理入口 |
| 辅助线 | `#AEB8C5` | 分隔线、输入框边界 |

不使用大面积渐变、玻璃拟态、紫色霓虹或浮动光球。圆角只用于按钮、输入控件和少量可点击状态块；页面骨架使用直线、边框和留白。

### 3.2 字体

- 标题：使用较硬朗、偏窄的无衬线字体，形成清楚的层级和工程感。
- 正文：使用系统中文无衬线字体，保证长段落和题目易读。
- 题号、状态编号和时间：使用等宽字体，便于扫描。

不再使用当前界面的大号衬线标题作为主要识别元素，避免页面像文章模板或宣传页。

### 3.3 统一视觉元素

三页都保留左侧进度栏，桌面端固定为窄栏，移动端折叠为顶部横向进度条。进度栏内容随页面变化，但样式和位置保持一致。

进度栏使用用户能理解的中文：

| 页面 | 进度栏标题 | 步骤示例 |
| --- | --- | --- |
| 首页 | 准备进度 | 上传简历、检查项目内容、开始面试 |
| 答题页 | 答题进度 | 项目经历、方案选择、故障排查、生成报告 |
| 报告页 | 报告内容 | 整体情况、回答较好的地方、可以改进的地方、评分说明 |

程序内部的 `Evidence Rail`、`Rubric`、`batch_id`、`SHA-256` 等术语不作为主界面文案。必要的技术信息放入报告页的可展开详情或页脚。

## 4. 页面布局

### 4.1 首页：准备面试

左侧为准备进度，右侧为主要工作区。

主要结构：

1. 页头：品牌名 Echo Offer，右侧显示“准备面试”。
2. 左栏：上传简历、检查项目内容、开始面试三步。
3. 右侧上部：标题“先把项目说清楚。”，说明简历只是起点，项目内容可以修改。
4. 右侧下部：文件上传、项目内容表和 AI 项目分析结果。
5. 主按钮：`确认项目，开始面试`。

字段文案采用用户语言：

- `个人职责` 改为 `你负责的部分`
- `核心方案` 改为 `主要方案`
- `工程难点` 改为 `遇到的难点`
- `量化结果` 改为 `最终结果`

分析完成后可以保留项目问题编辑，但用“个性化问题”或“根据项目生成的问题”描述，不出现“模型引用证据”等系统语言。

### 4.2 答题页：完成面试

左侧显示答题进度，右侧保持单一主任务，减少同时出现的卡片。

主要结构：

1. 页头：Echo Offer，显示“第 3 题，共 8 题”。
2. 左栏：已完成题目、当前题目、后续报告状态。
3. 主区：题目类别、题目正文、回答输入框、操作按钮。
4. 侧边说明：使用“答题说明”，告诉用户回答会保存，全部答完后统一生成报告。
5. 操作：`保存并继续`、`我不知道`、`跳过`。

“锚题、无提示首答、盲评分”等内部概念不放在醒目位置。需要保留产品事实时，改成“本题不提供提示”和“回答会原样保存”。

### 4.3 报告页：查看结果

报告页从“先看证据，再谈能力”改为更直接的用户表达：

> 看看哪些地方答得好，哪些还可以补充。

主要结构：

1. 页头：Echo Offer，显示“本场报告”。
2. 左栏：整体情况、回答较好的地方、可以改进的地方、评分说明。
3. 摘要区：完成题目、回答较好、需要加强三个简明指标。
4. 题目反馈：显示题号、等级、回答摘录和评分理由。
5. 下方继续展示优势、可改进项和报告说明。

主界面不出现“Rubric 证据”“有效证据数”“可信边界”等词。对应内容改成：

| 原文案 | 新文案 |
| --- | --- |
| Rubric 证据 | 回答摘录 |
| 可信边界 | 评分说明 |
| 平均证据置信度 | 参考程度 |
| 评估状态 | 报告状态 |
| 模型说明 | 结果说明 |

“参考程度”只在需要解释评分可靠性时显示，并用普通话说明，不作为大号成绩展示。

## 5. 等待、错误和重试

### 5.1 生成报告中

不显示虚假的百分比，不展示“请求模型、校验证据”等内部流程。

页面文案：

- 标题：`正在生成本场报告。`
- 说明：`所有回答都已保存。生成报告可能需要一会儿，请保持页面打开。`
- 步骤：`保存 8 道回答`、`整理回答`、`生成报告`

当前步骤使用一条低调的扫描线，尊重 `prefers-reduced-motion` 设置。

### 5.2 请求超时

错误页面不使用大面积红色警报，也不让用户重新答题。

页面文案：

- 标题：`这次没有拿到评分结果。`
- 原因：`模型服务响应较慢`
- 说明：`回答已经保存，不需要重新答题。可以直接再试一次，也可以稍后回来。`
- 主按钮：`重新生成报告`
- 辅助操作：`返回首页`
- 状态提示：`8 道回答已保存`

### 5.3 其他失败

鉴权失败、服务暂时不可用、网络连接失败等错误沿用现有错误码，但统一转换为用户可理解的短句。技术错误码只进入开发日志或可展开详情，不直接展示给用户。

## 6. 响应式和无障碍

- 桌面端使用左栏加工作区布局，最大内容宽度控制在可读范围内。
- 移动端左栏折叠为顶部进度条，答题页操作栏固定在底部。
- 输入框、按钮和链接必须保留清晰的键盘焦点样式。
- 颜色不能作为唯一状态信号，当前步骤同时使用文字和位置变化表达。
- 减少动态效果时关闭扫描动画，不影响流程和信息理解。
- 长题目、长回答和错误文案允许自然换行，不用截断代替布局处理。

## 7. 交互与数据边界

本次重设计不修改以下现有行为：

- 每道题提交后只保存回答，不逐题调用 AI。
- 全部问题完成后统一生成一次评分报告。
- 评分失败后可以重新生成，不重复保存回答。
- 跳过的题目不产生等级，明确回答“不知道”仍按有效首答处理。
- 报告继续展示每题等级、回答摘录、评分理由和状态。

UI 只负责展示这些状态，不在前端自行计算等级或改变后端评估结果。

## 8. 验收标准

1. 三页使用同一套颜色、字体、边框和进度栏结构。
2. 页面主文案不出现 `Evidence Rail`、`Rubric`、`冻结事实`、`可信边界` 等内部术语。
3. 首页能清楚完成上传、检查项目和开始面试。
4. 答题页能清楚看到当前题目、完成进度和保存动作。
5. 报告页能从回答摘录和评分理由理解每题结果。
6. 评分等待和超时页面不会暗示回答丢失，也不会引导用户重新答题。
7. 移动端无横向溢出，题目、输入框和底部操作均可用。
8. 现有前后端测试继续通过，前端类型检查和生产构建继续通过。

## 9. 范围外事项

- 不增加新的 AI 模型或评分算法。
- 不改简历解析协议和批量评分接口。
- 不增加登录、历史场次、跨场能力画像等功能。
- 不同步到 GitHub。
