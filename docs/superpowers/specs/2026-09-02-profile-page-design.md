# 用户画像页面设计

## 目标

在现有本地单用户面试应用中增加一个可访问的用户画像页面，让用户看到不同求职方向下的能力变化和下一步学习建议。页面只读取已经保存的结构化画像数据，不在打开页面时调用模型。

## 页面入口与范围

- 页面路径为 `/profile`。
- 首页、模型设置页和面试记录页都提供“用户画像”入口。
- 一个用户可能有多个方向、级别或目标岗位，页面从已保存的面试记录中整理可用画像并允许切换。
- 若没有完成过面试，展示空状态并引导用户先开始一场面试。

## 页面结构

页面采用“方向选择 + 当前画像”结构，而不是通用数据看板：

1. 顶部保留现有品牌和页面导航。
2. 左侧展示已保存的求职方向、级别、目标岗位和最近更新时间；移动端改为横向可滚动的选择列表。
3. 右侧展示当前画像：求职方向、目标岗位、系统根据有效回答整理出的总结，以及最近更新日期。
4. 能力部分按技能行展示技能名称、0～4 等级、目标等级、有效回答次数、可信程度和最近变化。等级使用五格点位表达，不显示 0～100 总分。
5. 学习建议按优先级排列，显示原因、行动步骤和完成标准；用户可以把建议标记为“开始练习”“已完成”或“暂时放一放”。
6. 页面底部展示画像快照时间线，用于查看多次面试后的能力变化，不额外生成自然语言总结。

## 数据流

页面首次加载 `GET /api/interviews/history`，按 `profile_id` 去重得到画像选择项。选择画像后并行读取：

- `GET /api/profiles/{profile_id}/summary`
- `GET /api/profiles/{profile_id}/history`

更新建议状态时调用 `PATCH /api/recommendations/{recommendation_id}`，成功后只更新当前建议状态，不重新加载或调用模型。

历史记录接口补充 `profile_id`，使历史页面可以直接链接到对应画像。已有画像汇总接口、数据库模型和批量评分后的画像更新逻辑保持不变。

## 文案与状态

- 使用“能力概况”“答得好的地方”“还可以补上的地方”“接下来练什么”等自然表达。
- 不在用户界面展示“冻结事实”“盲评分器”“证据链”“画像快照”等内部实现术语。
- 加载、无画像、接口失败、无能力数据、无学习建议都提供明确的下一步操作。
- 页面不突出总分，强调能力等级、有效回答次数、变化趋势和可执行建议。

## 验收标准

- 从首页、模型设置页和面试记录页可以进入 `/profile`。
- 多个画像可以切换，切换后能力与建议内容对应变化。
- 画像页面能正确处理空数据、加载失败和建议状态更新失败。
- 页面不新增 AI 请求，不显示内部评估术语，不出现 0～100 总分。
- 后端历史记录返回 `profile_id`，现有后端和前端测试全部通过，生产构建通过。
