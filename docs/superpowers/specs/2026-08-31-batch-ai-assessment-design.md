# Echo Offer 批量 AI 评分设计

日期：2026-08-31

状态：已确认设计，待实现

## 1. 背景与目标

当前实现会在每次提交回答时调用一次 AI 评分器。一次面试包含多道题，这会带来多次模型请求、较高调用成本和被模型延迟打断的面试体验。

本次改动将评分时机调整为：面试过程中只保存回答，全部问题完成后集中调用一次模型，返回每道题的独立评分。目标是在不改变盲评分、证据完整性校验和确定性聚合规则的前提下，将一场面试的 AI 评分调用次数降为一次。

## 2. 已确认的范围

### 2.1 包含内容

- 回答提交接口不再触发 AI 评分。
- 新增本场面试的批量评估接口。
- 一次 SiliconFlow 请求携带本场待评估的问题、冻结 Rubric 和回答。
- 模型为每个问题返回独立的 Rubric 评分、证据区间和置信度。
- 后端逐题校验模型输出，并为每道题保存评估运行和 Rubric 观察。
- 最后一题完成后，前端自动发起批量评估。
- 提供评估阶段进度、失败提示和重新生成评估操作。
- 评估失败时保留所有回答，重试不新增回答记录。

### 2.2 不包含内容

- 不在本次改动中实现语义证据相关性验证器。
- 不在本次改动中实现技术事实核验器。
- 不在本次改动中实现跨场次画像或追问引擎。
- 不展示未经校准的 0～100 综合分数。
- 不自动推送 GitHub、创建 Pull Request 或改变远程仓库。

## 3. 用户流程

1. 用户进入面试并回答问题。
2. 每次提交回答时，后端仅保存回答文本、回答状态和幂等标识，返回 `assessment: null`。
3. `submitted` 和 `explicit_unknown` 都视为已完成；`skipped` 也结束当前问题，但不进入 AI 评分。
4. 最后一题提交后，前端自动启动本场批量评估，并显示进度。
5. 后端收集本场回答，创建待评估状态，并调用一次 SiliconFlow 批量评分。
6. 后端校验每道题的结果，保存有效评估或审计无效证据。
7. 前端收到完整结果后进入报告页，展示逐题等级、有效证据、覆盖率和置信度。
8. 如果模型调用失败，页面提示回答已保存，并提供“重新生成评估”。重试只创建新的评估尝试，不创建新的回答。

## 4. 后端接口与数据流

### 4.1 回答接口

保留现有接口：

`POST /api/sessions/{session_id}/answers`

改动后的职责：

- 校验问题属于当前面试。
- 按 `client_submission_id` 保证幂等。
- 保存回答文本和状态。
- 不调用 `AssessmentProvider`。
- 返回回答记录以及空的评估字段。

同一回答重复提交时，返回已有回答，不追加新回答。评估重试由批量评估接口负责。

### 4.2 批量评估接口

新增接口：

`POST /api/sessions/{session_id}/assessment`

接口行为：

- 只有本场所有问题均已结束时才允许执行；未完成时返回明确的缺题信息。
- 已有有效批量评估时直接返回已有结果，不再次调用模型。
- 存在失败、拒绝或未完成评估时，允许重新创建一次评估尝试。
- 收集 `submitted` 回答交给模型。
- `explicit_unknown` 按当前评分规则产生等级 0 的有效 Rubric 观察，不额外调用模型。
- `skipped` 不产生有效评分。
- 一次模型请求返回多个问题的结果。
- 返回本场评估状态和每道题的评估结果。

批量模型输入使用独立 case 列表。每个 case 只包含：问题文本、问题类别、知识点 ID、冻结 Rubric 和当前回答。提示词明确要求 case 之间独立评分。不会携带简历全文、历史画像、过去分数、薄弱点或下一题优先级。

### 4.3 批量模型输出

模型必须只返回合法 JSON，结构表达每个问题的结果，并包含：

- `question_id`
- `answer_id`
- 每个 Rubric 的 `rubric_id`
- `level`，范围为 0～4
- `evidence_start`、`evidence_end`
- `quoted_text`
- `confidence`，范围为 0～1

程序负责检查：问题和回答 ID 是否完整、Rubric 是否完整且不重复、区间是否能切出原回答文本、引用文本是否相等、回答 SHA-256 是否一致。模型不能直接决定最终聚合分数。

### 4.4 持久化

继续使用 `AssessmentRun` 和 `RubricObservation`：

- 每个回答对应一个本次批量评估的 `AssessmentRun`。
- 同一批量调用产生的多个运行共享同一批次标识，便于审计和报告查询。
- 运行状态使用 `pending / valid / invalid / rejected`。
- 模型连接、超时、鉴权和格式错误保留具体错误码。
- 无法定位的证据保留为 `invalid`，记录原因，不静默删除。
- 只有有效运行的 Rubric 观察进入报告统计。

## 5. 前端交互

面试页行为调整为：

- 普通提交：显示“回答已保存”，不显示逐题 AI 分数。
- 最后一题完成：进入“正在生成本场评估”状态。
- 进度阶段显示为：`收集回答 → 请求模型 → 校验证据 → 生成报告`。
- 批量评估成功后跳转报告页。
- 失败时保留当前面试上下文，显示“回答已保存，评估未完成”，提供“重新生成评估”。
- 重试按钮只请求批量评估接口，不重新提交最后一个回答。

报告页继续展示逐题 Rubric 证据、等级、置信度和评估状态，不增加 0～100 总分。

## 6. 错误处理与边界

- 面试未完成：拒绝批量评估并返回缺少的问题列表。
- 没有任何可评分回答：生成空报告，不调用模型。
- 模型超时或连接失败：所有回答保留，相关评估保持 `pending`，返回可重试错误码。
- 模型返回非法 JSON、缺题、重复 Rubric 或证据哈希不匹配：本次评估不进入 `valid`，保存审计信息并允许重试。
- 已成功评估的面试再次打开报告：读取已保存结果，不重复调用模型。
- `explicit_unknown` 不是无回答；它是有效首答，按等级 0 记录。
- `skipped` 不转换为等级 0。

## 7. 测试策略

后端测试覆盖：

- 提交单题不会调用评分 Provider。
- 全部问题完成后批量接口只调用 Provider 一次。
- 批量结果能按问题和回答正确持久化。
- `submitted`、`explicit_unknown`、`skipped` 的处理符合规则。
- 已完成评估重复请求不会再次调用模型。
- 模型失败后回答仍存在，重试不产生新回答。
- Provider 错误码被保留。
- 批量输出的缺题、重复 Rubric、非法等级、证据偏移和哈希错误会被拒绝或标记为无效。
- 报告只统计有效评估。

前端测试和验证覆盖：

- 类型契约包含批量评估响应。
- 面试完成状态能进入批量评估状态。
- 评估失败时能展示重试入口。
- 生产构建通过。

## 8. 验收标准

- 一场包含多道题的面试，在回答过程中模型调用次数为 0。
- 全部问题完成后，模型调用次数为 1。
- 报告能看到每道题的独立等级、证据和置信度。
- 重新打开已完成报告不会产生新的模型调用。
- 模型失败不丢失回答，重试不会增加回答数量。
- API Key 只从后端环境变量读取，不进入前端代码、日志、数据库或 Git 提交。
