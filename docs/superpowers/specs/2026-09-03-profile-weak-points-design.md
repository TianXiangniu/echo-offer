# “我还要补什么？”能力概况重设计

## 1. 背景

当前 `/profile` 页面同时展示方向、能力等级、建议、状态和历史快照。数据完整，但用户打开页面后仍然需要理解“能力等级”“稳定程度”和“推荐状态”这些系统概念，才能知道下一步该做什么。

本次重设计把页面的主要任务收窄为：根据已经完成的面试，告诉用户哪些地方值得回看，以及如何回到当时的真实回答。页面继续支持多个求职方向，但不再把“用户画像”作为用户必须理解的概念。

## 2. 目标与非目标

### 目标

- 首屏直接回答“下一次先练什么”。
- 按技能主题整理薄弱项，并展开到具体面试问题。
- 每个问题显示为什么需要补充，以及对应的练习建议。
- 支持从薄弱项回到产生它的历史面试结果，并定位到对应问题。
- 保留已有的长期画像、面试历史、建议状态和多求职方向能力。
- 不增加新的模型请求，不把内部评分术语暴露给用户。

### 非目标

- 本次不增加专项练习流程。
- 本次不改评分模型、Rubric、评分等级或 100 分计算方式。
- 本次不增加雷达图、复杂趋势图或新的统计指标。
- 本次不删除数据库中的画像快照和面试记录。

## 3. 用户界面

### 3.1 页面命名和首屏

页面主标题改为：

> 我还要补什么？

辅助说明改为：

> 根据最近几场面试，整理出最值得回看的地方。

导航中的“能力概况”可以改成“我还要补什么”，避免用户以为这里是抽象的个人档案页。

首屏保留当前求职方向和已参考的面试场次数，但不展示“画像”“稳定程度”“有效样本”等系统词汇。

### 3.2 主内容结构

页面主体按优先级分为三个区域：

1. **优先回看**：高优先级薄弱项，通常是表现与岗位要求差距较大，或曾出现严重错误的方向。
2. **接着练**：有明显缺口，但暂时不需要优先处理的方向。
3. **再答几次看看**：数据还少，当前结论不稳定的方向。

已经达到当前岗位要求的方向不放在主清单里，避免页面重新变成技能目录。若后续需要查看完整能力列表，可以从页面次级入口进入，不纳入本次实现。

### 3.3 薄弱项卡片

每个卡片按以下顺序展示：

```text
技能主题 · 优先回看
具体面试问题

为什么需要补
用一句自然语言说明回答中缺少的部分

建议怎么练
一到三条可执行建议

[查看这次回答]       [标记为练习中]
```

界面使用“查看这次回答”“标记为练习中”“暂时放一放”等用户动作词，不显示 `priority`、`status`、`profile_snapshot`、`last_session_id` 等内部字段名。

卡片中的“具体问题”必须来自已有的面试题，不能由前端根据技能名称临时拼接。没有找到对应有效回答时，显示“还没有足够的回答可以判断”，并隐藏“查看这次回答”按钮。

### 3.4 历史结果跳转

“查看这次回答”跳转到：

```text
/report/{source_session_id}#question-{source_question_id}
```

报告页为对应问题的内容容器增加稳定的 `id`，打开后浏览器可以定位到这道题。跳转目标不存在时仍打开整场报告，不阻塞用户查看其他结果。

### 3.5 空状态和异常状态

- 没有任何能力记录：显示“完成一场面试后，这里会告诉你下一步先练什么”。
- 有记录但没有高/中优先级缺口：显示“目前没有需要优先补的地方，继续保持并积累新的回答”。
- 某个来源面试已被隐藏：保留薄弱项，但不显示失效的跳转按钮；用户仍然可以看到问题和练习建议。
- 接口加载失败：说明是能力记录读取失败，并提供“再试一次”。不显示伪造的薄弱项。

## 4. 数据和接口设计

### 4.1 推荐项补充来源信息

扩展 `LearningRecommendationResponse`，新增以下可空字段：

- `source_session_id`: 产生该建议的最近一场有效面试。
- `source_question_id`: 该方向中表现最弱的具体问题。
- `source_question`: 问题原文。
- `source_answer_excerpt`: 回答的可展示片段。
- `source_level`: 该问题的 0～4 等级，仅供前端做自然语言展示，不作为新的评分来源。

前端 `LearningRecommendation` 同步增加这些字段。字段为空表示当前没有可追溯来源，前端必须按空状态处理。

### 4.2 来源数据的确定规则

来源数据由后端从已有数据库记录派生，不增加 AI 请求：

1. 以当前画像的 `CandidateKnowledgeState.last_session_id` 作为优先查找范围。
2. 找到该场与技能对应的面试题，以及状态为 `submitted` 或 `explicit_unknown` 的回答。
3. 只使用最新一次、状态为 `valid` 的 `AssessmentRun`。
4. 如果同一技能对应多个问题，选择 `aggregate_level` 最低的问题；等级相同则选择面试题顺序靠前的问题。
5. 从该问题的回答文本开头截取最多 240 个字符作为 `source_answer_excerpt`，不重新调用模型，也不生成不存在的事实。
6. 找不到有效评估时，所有来源字段返回 `null`。

这样可以保证每一条薄弱项都能回到真实的题目和回答，同时不会让历史画像进入盲评分器。

### 4.3 数据库变更

本次不增加数据库表和持久化字段。来源信息根据 `CandidateKnowledgeState`、`InterviewSession`、`InterviewQuestion`、`AnswerAttempt`、`AssessmentRun` 和 `RubricObservation` 查询得到。

### 4.4 现有字段的使用

- `priority` 只用于后端排序和前端分区，不直接显示。
- `reason`、`actions` 和 `success_criteria` 继续作为建议内容来源，但需要通过自然中文呈现。
- `status` 的交互继续保留，状态更新接口不变。
- 画像能力等级和历史快照接口保持兼容，其他页面不受影响。

## 5. 前端组件调整

继续使用现有 `/profile` 路由和多方向选择器，重做右侧主体内容：

- `ProfilePage`：负责加载方向和当前画像。
- `WeakPointSummary`：展示当前方向和薄弱项数量。
- `WeakPointSection`：按“优先回看 / 接着练 / 再答几次看看”分区。
- `WeakPointCard`：展示主题、具体问题、原因、练习建议和历史跳转。
- `RecommendationStatusAction`：复用现有建议状态更新逻辑。

组件只接收已经整理好的响应数据，不在前端计算能力等级、缺口优先级或评分结果。

## 6. 文案原则

- “能力概况”改成“我还要补什么”。
- “能力等级”只在需要解释时显示为“最近表现”，不作为首屏主标题。
- “有效回答”“稳定程度”“画像快照”“推荐状态”不直接出现在用户主界面。
- “查看原回答”统一改为“查看这次回答”，因为目标是回到一场真实面试。
- 解释问题时使用“你当时提到了什么、还缺什么”，不使用“模型判断”“证据覆盖率”等系统表达。
- 没有数据就明确说“还不够判断”，不把缺失数据写成低分。

## 7. 测试和验收

### 后端

- 测试推荐项能够返回来源面试、来源问题和回答片段。
- 测试只选择有效评估，`pending`、`invalid`、`rejected` 不得成为来源。
- 测试多个问题属于同一技能时，选择最低等级且结果稳定的来源。
- 测试没有来源时字段为 `null`，接口仍能正常返回。
- 运行现有后端全量测试，确认历史、评分、画像和报告接口不回归。

### 前端

- 测试页面包含“我还要补什么”“优先回看”“查看这次回答”等自然文案。
- 测试不显示内部评分和画像术语。
- 测试来源字段为空时隐藏跳转按钮并显示空状态。
- 测试来源跳转包含 `/report/{session_id}#question-{question_id}`。
- 测试桌面端和移动端卡片布局，键盘焦点和减少动态效果设置保持可用。
- 运行前端测试和生产构建。

### 验收标准

用户进入能力页面后，不需要理解“用户画像”或“能力状态”的概念，就能在首屏找到至少一个可回看的具体问题；点击后能回到对应历史面试；如果没有足够数据，页面会说明原因，而不是给出看似精确的判断。

## 8. 实施顺序

1. 先补充后端来源字段和来源查询规则。
2. 为报告页增加问题定位锚点。
3. 重做能力概况页面的薄弱项布局和自然文案。
4. 更新接口类型、契约测试和 README。
5. 运行后端全量测试、前端测试和生产构建，再进行浏览器验收。
