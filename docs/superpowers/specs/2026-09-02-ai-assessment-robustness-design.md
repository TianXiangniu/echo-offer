# AI 评分稳定性设计

## 目标

让简历分析和整场面试评分在模型偶发输出不完整、带解释文本、证据引用不精确或响应变慢时，能够给出可诊断的错误，并尽量保留已经成功的评分结果。

## 设计

### 1. 模型输出与程序派生字段分离

模型只返回 `rubric_id`、`level`、`confidence` 和可选的 `quoted_text`。`evidence_start`、`evidence_end`、`answer_text_hash` 由程序根据回答原文自动计算，避免让模型计算中文字符串下标。

无法在回答中定位的引用保留为 `invalid`，不使其他题目一起失败。

### 2. 统一 JSON 提取与响应诊断

增加共享的模型输出处理：支持纯 JSON、Markdown JSON 代码块和带 `<think>` 的结果；拒绝空响应；识别 `finish_reason=length` 并记录为输出截断。所有解析错误都保留具体错误码和安全的响应摘要，不能记录 API Key。

### 3. 批量评分容错

整场评分仍然只在面试结束后调用模型，但把题目按小批次提交。每个批次独立成功或失败；成功批次写入评分，失败批次写入错误状态。只要存在可用评分，就生成 `partial` 报告；全部批次成功时生成 `ready` 报告。

### 4. 任务恢复与前端展示

本地同步请求产生的 `pending/running` 任务如果超过超时阈值，下一次请求将其标记为失败并允许重新评分。前端读取根级 `job_error_code/job_error_message`，显示超时、输出截断、JSON 格式、证据定位等真实原因。

## 不变约束

- 不上传或打印 API Key。
- 不把 `skipped` 当成 0 分。
- 评分仍然基于冻结 Rubric，最终等级仍由程序聚合。
- 保留现有本地 SQLite 数据，不要求重置数据库。

## 验收标准

- 模型返回代码块 JSON 时可以解析。
- 模型返回 `finish_reason=length` 时能明确报告“输出被截断”。
- 证据引用无法定位时只使对应 Rubric 无效，其他题目仍可进入部分报告。
- 8 道题评分被拆成多个批次；一个批次失败不会抹掉其他批次的有效评分。
- 卡死的 `running` 任务可以被下一次请求恢复。
- 前端显示根级错误，不再只显示“这次没有拿到结果”。
