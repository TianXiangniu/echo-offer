# 对话式面试官 v2 —— 全场对话流设计（dialog-interview v2）

> **实施状态（2026-09-05）：** 全部完成并真机验证。**追加完成"面试统一"**：classic 会话的 timeline 补建（知识问答+追问+教练便签）——所有会话类型统一渲染为暗色紧凑聊天流，旧卡片/表单 UI 退役；输入坞按输入模式分派（追问回答/阶段对话/知识作答），含"悄悄说"教练便签与打字指示器。迁移 0013（project_dialogs + sessions.stage/mode/dialog_rounds）、dialog_flow.py 状态机（intro→深挖→knowledge→wrap_up，动态收束 + 降级保护）、面试官指南 prompt（interviewer-v1）、深挖评分 case（project.deep_dive，权重 1.5/1.5）、三条新 API、前端消息时间线（对话气泡 + 阶段指示器 + 降级按钮）、知识题项目化衔接（静态模板）。真机走完整场三阶段对话面试：深挖追问引用候选人上轮具体内容（数字质疑生效），敷衍回答被锚点评出 38 分（锚点生效实证）。回归 211 项 pytest + 前端全绿。一处实施调整：会话创建增加 mode 参数（classic/dialog），classic 完全保留旧流程供存量与测试使用。

> **v2 核心转变：** v1 是"给现有面试加一个对话功能"，v2 是"把整场面试重构成真实对话"。
> **一句话：** 打开面试页，看到的就是一个聊天流——面试官的每句话（自我介绍后的开场、项目深挖、知识问题、反问）都按真实节奏出现，候选人逐段作答。表单消失了，但底层的评分、知识库、画像机制全部保留。

**设计原则：**

1. **渲染统一，数据分层。** UI 上一切都是对话消息；数据层保持现有结构（知识题仍是 interview_questions，深挖仍是 dialog 轮），由统一的"面试时间线"视图组装。不推翻已验证的评分与题目机制。
2. **动态节奏。** 深挖轮数由面试官按"信息饱和度"动态收束，程序只设上限（8）与下限（4）保护。
3. **面试中绝不评分**（盲评纪律不变）；评分发生在整场对话结束后。
4. **流程不卡死**：任何生成失败都有静态降级。
5. **存量兼容**：`stage` 默认 `knowledge`，旧会话行为不变。

---

## 一、全场对话流（渲染层统一）

面试页不再是"一张题目卡片 + 表单"，而是一条**消息时间线**：

```
[面试官] 先做个简单的自我介绍吧。                        ← 开场轮
[候选人] （完整自我介绍）
[面试官] 你简历里这个企业知识库项目，当时的背景是什么？    ← 深挖轮（实时生成）
[候选人] ……
[面试官] 你说命中率提升 18%——这个数字是怎么测的？基线呢？ ← 深挖轮（数字质疑）
[候选人] ……
[面试官] 好的。那我们换个话题：如果 RAG 召回了很多无关内容，你会怎么定位？  ← 知识题（预生成，带项目化衔接语）
[候选人] ……
[面试官] 最后，你有什么想问我的吗？                      ← 反问轮
```

**关键：三种内容在 UI 上无差别**，候选人感知就是一场连续的对话：

| 消息类型 | 生成方式 | 数据来源 |
|---|---|---|
| 开场（自我介绍） | 固定模板句 | 无 |
| 深挖轮 | 实时生成（面试官模型） | project_dialogs |
| 知识题 | 预生成 + 项目化衔接语 | interview_questions（现有机制不动） |
| 知识题的追问 | 现有追问 decide 机制 | interview_followups（不动） |
| 反问 | 固定模板句 | 无 |

候选人回答仍逐条落库、不可修改（现有不可变原则）。**评分机制完全不变**：知识题逐题评、深挖整段评——变的只是渲染和交互。

## 二、阶段状态机（v2 修订）

```
intro（1 轮）→ project_dialog（4-8 轮，动态收束）→ knowledge（现有 5 题）
→ wrap_up（1 轮反问，可跳过）→ 评分 → 报告
```

- `sessions.stage`：`intro` → `project_dialog` → `knowledge` → `wrap_up` → `completed`
- 存量会话 `stage="knowledge"` 默认值：一切旧行为不变。
- 知识阶段完成后**自动**进入 wrap_up（无需手动触发）。

## 三、项目深挖：动态收束 + 自适应深度

### 3.1 面试官指南（替代 v1 的策略标签）

v1 让模型每轮从 8 条策略里"选一个打标签"——把即兴发挥模板化了。v2 把策略库升级为**面试官指南**（写进 system prompt 的技巧说明，模型自由运用）：

```
你是这场面试的面试官。深挖项目时，像真实面试官一样即兴选择角度：
- 听到量化结果，追问测量方式和基线（"18% 怎么测的？"）
- 听到选型，追问放弃过的备选方案
- 听到架构，做假设变化（"QPS 涨 10 倍还成立吗"）
- 职责描述含糊时，追问分工边界
- 候选人答得好的方向继续深挖一层；答不上来的方向换个角度再试一次，不要反复纠缠
- 连续两轮不要用同一种问法；每次只问一个问题，不要一次抛出多个
```

程序侧仍保留一个启发式标签（数字质疑/假设变化/…，由简单的关键词规则打）仅用于**报告复盘展示**，不进入 prompt、不约束模型。

### 3.2 动态收束（信息饱和度）

- 每轮生成下一句时，面试官同时输出 `"saturated": true|false`——判断该项目关键信息（背景/职责/方案/取舍/验证/结果）是否都已挖到。
- `saturated=true` 且轮数 ≥ 4 → 面试官输出收束句，阶段推进到 knowledge。
- 程序硬约束：轮数 < 4 不允许收束（保证深挖量）；轮数 ≥ 8 强制收束（保护成本）。
- 候选人随时可点"跳过剩余深挖"提前进入知识阶段。

### 3.3 自适应深度

面试官指南中加入因材施问：4 级回答引出更深的假设题；1-2 级回答换更基础的问法再给一次机会——**评分不动，但路径因人而异**，这是真实面试和问卷最大的区别。

## 四、知识题的项目化衔接（低成本高感知）

知识题题干本身**不改**（评分锚点和题库稳定），但每道知识题出现前，由对话机制生成一句**衔接语**（单独一次轻量调用，或与收束句合并）：

- 输入：候选人项目对话摘要 + 下一道知识题
- 输出：一句话衔接，如"你说检索是项目里最难的环节。那我们脱离你的项目看一个通用问题——如果召回了很多无关内容，你会怎么定位？"
- 衔接语存 `project_dialogs`（role=interviewer，strategy="bridge"），渲染在知识题气泡之前。
- 生成失败降级：不显示衔接语，直接出题（流程不卡死）。

## 五、评分与对话复盘

- 评分机制不变：知识题逐题、深挖整段（`project.deep_dive` 大 case，rubric 权重 mechanism 1.5 / engineering 1.5，reference_facts 为项目事实摘要）。
- **新增：对话复盘**（报告页新区块）——逐轮标注该轮面试官的追问角度（启发式标签）与候选人回答的等级变化，识别出：
  - **被问住的轮**：追问后回答质量明显下降的轮次（学习价值最高，链接到对应知识点 wiki）
  - **答出深度的轮**：追问后给出具体细节的轮次
  - 复盘由评分结果 + 轮次文本规则化生成（逐轮单独评分太贵——用每轮回答与该轮追问角度的对应关系做轻量规则标注），不引入新的模型调用。
- 深挖 case 评分失败不阻塞知识题分数（partial 机制已有）。

## 六、上下文管理

深挖 6-8 轮 + 项目事实 + JD，prompt 会变长。策略：

- 早期轮次（第 1-2 轮）在超过 4 轮后压缩为摘要（程序拼接："候选人此前介绍了：背景 X、方案 Y、结果 Z"）——纯程序拼装，不额外调模型。
- 最近 3 轮保留全文。
- 项目事实（确认表单 8 字段）始终全量注入（它是追问的锚）。

## 七、数据模型（迁移 0013）

```python
class ProjectDialog(Base):
    __tablename__ = "project_dialogs"
    id: str PK
    session_id: str FK, index
    turn_no: int                      # 全会话消息序（含开场/衔接/反问）
    role: str                         # "interviewer" | "candidate"
    content: Text
    kind: str                         # "intro" | "dialog" | "bridge" | "question_intro" | "wrapup"
    heuristic_tag: str | None         # 启发式追问角度（程序侧打，仅用于复盘展示）
    created_at: datetime

# sessions 新增：stage str default "knowledge"；dialog_rounds int nullable（实际轮数）
```

## 八、接口

```
POST /api/sessions/{sid}/dialog/answer    # {text}：存回答 → 按阶段生成下一句（深挖下一问/收束/阶段推进）
POST /api/sessions/{sid}/dialog/finish    # 提前结束当前对话阶段（深挖阶段专用）
GET  /api/sessions/{sid}                  # 视图新增 stage / timeline（统一消息流）/ dialogs
POST /api/sessions/{sid}/wrapup/skip      # 反问跳过 → 完成会话 → 评分
```

知识题的提交仍走现有 `/answers` 接口（数据层不动），前端按 stage 把它渲染为对话气泡。

## 九、前端

- 面试页重构为消息时间线组件：interviewer 气泡（左，含"追问/衔接/收束"角标）+ candidate 气泡（右）+ 底部输入区（随 stage 切换：自由文本 / 现有"不知道/跳过"按钮组）。
- 进度显示改为阶段指示器：`自我介绍 ✓ → 项目深挖（3/6）→ 知识环节（2/5）→ 反问`。
- 深挖生成下一句期间显示"面试官正在思考…"（3-8 秒）。
- 失败降级：静态备用问题 / 不显示衔接语。

## 十、明确不做

- 流式输出（单句生成 3-8 秒，加载态足够）
- 语音/打断式追问、多项目并行深挖、独立 HR 面
- 对话中的实时评分与实时提示（破坏盲评与真实性）

## 十二、验收标准

1. 新会话完整走通 intro → 深挖（动态收束）→ knowledge → wrap_up → 评分，score_100 可用。
2. 深挖轮数 ∈ [4, 8]（提前跳过除外），收束由 saturated 驱动。
3. 面试官下一句引用候选人上轮具体内容；知识题前出现项目化衔接语。
4. 深挖 case 证据引用落在对话文本内；评分失败不阻塞知识题分数。
5. 报告出现"对话复盘"区块（含被问住的轮 → 知识点 wiki 链接）。
6. 存量会话全部现有测试不改断言通过。
